# Розділ 9. Аналіз можливостей масштабування системи

Система розрахована на нерівномірне навантаження (пікові запити під час початку та завершення робочих змін). Для забезпечення стабільної роботи передбачено кілька стратегій масштабування.

### 1. Горизонтальне масштабування (Horizontal Scaling)

Завдяки використанню Docker та трирівневій архітектурі, рівень бізнес-логіки (Application Server на Node.js) може бути масштабований шляхом запуску додаткових екземплярів (instances) за балансувальником навантаження Nginx. Це дозволяє розподіляти HTTP-запити від мобільних додатків та турнікетів.

### 2. Масштабування бази даних

Оскільки основне навантаження при генерації звітів припадає на операції читання, передбачено:

- **Read Replicas:** Створення реплік PostgreSQL для розвантаження основного майстер-вузла. Сервіс звітів (Report Service) звертається до реплік, не сповільнюючи процес реєстрації приходу співробітників (Check-in).
- **Connection Pooling:** Використання PgBouncer для ефективного керування великою кількістю одночасних з'єднань з БД.

### 3. Кешування та асинхронність

- **Redis:** Використовується для зберігання активних сесій та часто запитуваних довідників (ролі, типи відпусток), що зменшує кількість звернень до дискової підсистеми БД.
- **Черги повідомлень (Message Queues):** Для обробки подій від турнікетів у пікові години передбачено впровадження черг, що дозволяє Attendance Service приймати події негайно, а записувати їх у БД — поступово, уникаючи блокувань.

### 4. Вертикальне масштабування

На початкових етапах впровадження (для малих та середніх компаній) потужність системи може бути збільшена шляхом додавання ресурсів (CPU, RAM) на сервері бази даних, що є найбільш економічно ефективним методом до досягнення лімітів продуктивності обладнання.
